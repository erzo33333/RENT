# ADR-001: Выбор архитектурного стиля

- **Статус:** Принято
- **Дата:** 2026-10-05
- **Решение:** Модульный монолит с единой реляционной базой данных PostgreSQL

## Контекст

Разрабатывается веб-приложение для учёта и мониторинга арендного жилья. Основные пользователи — арендодатель и арендатор.

Система включает связанные функции: управление объектами недвижимости, проживающими, договорами, платежами, имуществом, показаниями счётчиков, уведомлениями, заявками и аналитикой.

В Практической работе №1 выбран технологический стек: Java/Spring, Vue, PostgreSQL и Docker.

## Рассмотренные варианты

1. Монолитное приложение без внутреннего логического разделения.
2. Микросервисная архитектура с независимыми сервисами.
3. Модульный монолит — единое приложение с разделением на логические модули.

## Решение

Выбран **модульный монолит**.

Серверная часть реализуется как единое Spring-приложение. Внутри выделяются модули:

- объекты недвижимости;
- арендаторы и пользователи;
- договоры;
- платежи;
- имущество;
- показания счётчиков;
- заявки и уведомления;
- отчётность и аналитика.

Для хранения данных используется единая база PostgreSQL.

Клиентская часть реализуется на Vue и взаимодействует с серверной частью системы.

Развёртывание выполняется с использованием Docker.

## Обоснование

Микросервисная архитектура для текущего масштаба проекта создаёт дополнительную сложность: отдельное развёртывание, мониторинг, сетевое взаимодействие и обработка отказов.

Модульный монолит сохраняет простоту разработки и эксплуатации и одновременно разделяет код по ответственности. При дальнейшем росте отдельный наиболее нагруженный модуль потенциально может быть выделен в самостоятельный сервис.

## Последствия

### Положительные

- проще разработка и локальный запуск;
- проще тестирование и отладка;
- проще транзакционная работа с PostgreSQL;
- меньше инфраструктурных компонентов;
- логическое разделение функциональности;
- возможность дальнейшего выделения отдельных модулей.

### Отрицательные

- серверная часть разворачивается как единое приложение;
- отказ серверной части влияет на все функциональные модули;
- независимое масштабирование отдельных модулей ограничено;
- при значительном росте проекта может потребоваться распределённая архитектура.

## Связь с NFR

Выбранная архитектура поддерживает требования к сопровождаемости, производительности и масштабируемости:

- модульное разделение облегчает сопровождение;
- единое приложение уменьшает накладные расходы на взаимодействие компонентов;
- Docker стандартизирует развёртывание;
- архитектура допускает увеличение количества экземпляров серверной части при росте нагрузки.
