# Нефункциональные требования

## 1. Назначение

Нефункциональные требования определяют качественные характеристики информационной системы учёта и мониторинга арендного жилья и ограничения, предъявляемые к её реализации.

Система предназначена для арендодателей, сдающих в аренду объекты недвижимости. Она должна централизовать работу с объектами, договорами, платежами, имуществом, показаниями счётчиков и заявками арендаторов.

В проекте используются Java/Spring для серверной части, Vue для клиентской части, PostgreSQL в качестве СУБД и Docker для контейнеризации.

## 2. Производительность

| ID      | Требование                                                                                                    | Критерий проверки                                                                                                                   |
| ------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| NFR-P-1 | Система должна обеспечивать быстрый отклик при просмотре объектов, договоров, платежей и показаний счётчиков. | Не менее 95% основных API-запросов должны обрабатываться не более чем за 2 секунды при нагрузке до 100 одновременных пользователей. |
| NFR-P-2 | Формирование стандартных отчётов по доходам и расходам не должно требовать длительного ожидания.              | Отчёт за период до 1 года для 10 объектов формируется не более чем за 5 секунд.                                                     |
| NFR-P-3 | Поиск и фильтрация объектов должны сохранять приемлемую скорость при росте объёма данных.                     | 95% запросов поиска должны выполняться не более чем за 2 секунды при наличии до 10 000 объектов.                                    |

## 3. Доступность и надёжность

| ID      | Требование                                                                                   | Критерий проверки                                                                               |
| ------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| NFR-A-1 | Система должна быть доступна пользователям за исключением запланированных технических работ. | Доступность — не менее 99,5% времени в месяц.                                                   |
| NFR-A-2 | Подтверждённые данные не должны теряться при перезапуске или восстановлении приложения.      | После восстановления работоспособности 100% подтверждённых данных должны оставаться доступными. |
| NFR-A-3 | База данных должна регулярно резервироваться.                                                | Полная резервная копия создаётся не реже одного раза в сутки.                                   |
| NFR-A-4 | Система должна поддерживать восстановление после критического сбоя.                          | Целевое время восстановления — не более 4 часов; допустимая потеря данных — не более 24 часов.  |

## 4. Безопасность

| ID      | Требование                                                                                           | Критерий проверки                                                                                            |
| ------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| NFR-S-1 | Доступ к личным кабинетам должен предоставляться только после аутентификации.                        | 100% защищённых операций должны выполняться только аутентифицированными пользователями.                      |
| NFR-S-2 | Система должна разграничивать права арендодателя и арендатора.                                       | Арендодатель и арендатор могут выполнять только те действия, которые доступны их роли.                       |
| NFR-S-3 | Пароли не должны храниться в открытом виде.                                                          | Пароли хранятся только в виде криптографического хеша с использованием BCrypt.                               |
| NFR-S-4 | Передача учётных и персональных данных должна выполняться по защищённому соединению.                 | Для внешних запросов с чувствительными данными используется HTTPS/TLS.                                       |
| NFR-S-5 | Персональные данные должны обрабатываться с учётом требований проекта по защите персональных данных. | Доступ к персональным данным предоставляется только авторизованным пользователям с соответствующими правами. |
| NFR-S-6 | Изменения критически важных данных должны быть отслеживаемыми.                                       | Для изменений договоров, платежей и основных данных объектов фиксируются пользователь и время операции.      |

## 5. Масштабируемость

| ID       | Требование                                                                                                      | Критерий проверки                                                                                                       |
| -------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| NFR-SC-1 | Система должна сохранять работоспособность при увеличении числа объектов недвижимости.                          | Поддержка не менее 10 000 объектов без изменения основной модели предметной области.                                    |
| NFR-SC-2 | Система должна поддерживать рост исторических данных.                                                           | Поддержка не менее 1 млн записей о платежах, показаниях и событиях без потери основных требований к производительности. |
| NFR-SC-3 | Увеличение количества одновременно работающих пользователей не должно требовать полной переработки архитектуры. | Целевой рост до 500 одновременных пользователей должен достигаться преимущественно масштабированием серверных ресурсов. |

## 7. Сопровождаемость

| ID      | Требование                                                                                                   | Критерий проверки                                                                                                                |
| ------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| NFR-M-1 | Backend должен быть разделён на логические уровни и компоненты.                                              | Основная бизнес-логика, обработка HTTP-запросов и доступ к данным разделены на отдельные слои.                                   |

| NFR-M-3 | Изменения одного функционального модуля не должны приводить к необходимости переписывать несвязанные модули. | Архитектура должна обеспечивать слабую связанность модулей и прохождение существующих автоматизированных тестов после изменений. |
| NFR-M-4 | Система должна поддерживать контейнеризированное развёртывание.                                              | Приложение и его инфраструктурные зависимости должны запускаться средствами Docker в тестовой среде.                             |

| ID      | Требование                                                         | Критерий проверки                                                                                 |

| NFR-C-2 | Клиентская часть должна работать на ПК, планшетах и смартфонах.    | Основные пользовательские сценарии доступны при ширине экрана от 360 px.                          |

## 9. Связь с предметной областью

NFR сформированы на основании целевого процесса и функциональных требований системы. В текущем процессе основными проблемами являются отсутствие единой базы, ручной контроль договоров и платежей, ручной ввод показаний и отсутствие автоматизированной аналитики. Целевой процесс переносит эти операции в единую веб-систему, поэтому для неё критичны быстрый доступ к данным, сохранность информации, безопасность и возможность дальнейшего роста количества объектов.
